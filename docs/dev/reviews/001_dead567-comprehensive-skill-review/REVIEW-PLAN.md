## Review unit and criteria

U-001 is one complete standalone-package review, reported and committed as a coherent assessment. Its internal criteria groups are ordered below; they are not independent implementation tasks. The report must account for every current source file, positive coverage, failures, exclusions and evidence limits.

| Order / criterion | Scope | Criteria and evidence |
| --- | --- | --- |
| C-001 — Purpose, authority and discovery | SKILL.md; entry-facing metadata; current SPEC and capability map | Clear activation, effects, required context, direct routing, proportional selection, review/revision/structure-only boundaries and truthful completion. Source and routing inspection. |
| C-002 — Composition and module boundaries | All 20 reference files; entry; README | Sentence/paragraph/section/package composition, precise terms, referent availability, useful repetition, cohesive scope and substantive loading boundaries. Neither file length nor conventional headings are defects alone. |
| C-003 — Procedures and consequential handoffs | Manager; focused/genre modules and callers; mirrored governing recipes | Conditions, inputs, omissions, author decisions, evidence modes, acquisition versus corroboration, source/status distinctions, contextual outlines, revision comparison and docstring precedence. Inspect both sides of each consequential handoff. |
| C-004 — Package, presentation and tooling | Actual inventory, local links/anchors, YAML/SVG source, existing checker | Run authoring validator/inspector and bounded repository checks. Inspect checker scope and limitations; separate structural results from prose quality, host activation and visual rendering. |
| C-005 — Current documentation and observed use | README, SPEC, PLAN, capability map; fresh bounded tasks where justified | Agreement with actual package and capability boundaries. Retain a few positive/negative/variant observations without leaking expected answers to consumers. Do not rerun or reinterpret historical trial records as current results. |

## Included material and exclusions

Included: all runtime Markdown, optional presentation and icon, root README, current SPEC/PLAN/capability map, checker implementation and relevant live navigation. Review code only to establish its actual checking contract, not to extend the task into a tooling rewrite.

Excluded from editorial and compatibility review: closed review/revision plans and reports, historical validation records, Git internals, prior stopped checkout, external standards/web fact checking, live successful research campaigns, software-example execution, installation, and client display. Historical identities and paths may be inspected without reading their content. No finding is created merely because an old record describes an earlier snapshot.

## Scenarios and evidence boundaries

| Scenario | Intended contrast | Evidence method |
| --- | --- | --- |
| SC-001 | Review-only versus requested rewriting | Supplied local documentation task; report actual effects and stop. |
| SC-002 | Available source, unsupported quantity and unavailable citation | Supplied-content evidence task; distinguish access, support, criterion outcome and unresolved claim. |
| SC-003 | Available versus unavailable contextual references | Composition task with an identified local referent and an unidentified earlier revision. |
| SC-004 | Expository paragraph versus brief warning; conventional versus misleading heading | Supplied composition/outline material; no blanket length or heading rules. |
| SC-005 | Provisional notes versus definite commitment; source revision with missing factor | Bounded drafting/comparison task; preserve substantive conditions. |
| SC-006 | Valid package versus missing resource/anchor, where useful | Existing validators and isolated fixture copies; never mutate reviewed source. |

Scenarios are selected as supporting evidence, not as substitutes for reading all included source. Record source version, consumer context, resources loaded, actual outputs, observed actions and limitations. A reasoning exercise is not a target-client execution test. No claimed behavioral improvement is possible without a changed candidate and appropriate comparison.

## Findings and persistence

Allocate stable `R-001` etc. Each canonical finding records baseline path/line, observation, consequence, type, priority, confidence, bounded remedy/owner and an objective recheck. Keep suspected defects, recommendations and evidence gaps distinct. Record no-finding coverage as well.

At the end of U-001, consolidate assessments and verification, update HANDOFF, inspect the full authorized diff, commit the review result and publish/read back that checkpoint before any further campaign unit or commit. No source revision follows from a review finding alone. If publication fails, preserve the commit and recover the same operation; do not advance the campaign or claim published completion.

## Return boundary

Deliver the comprehensive report, canonical findings, suggested revision queue, actual checks and publication state. Stop for the human's revision decision. Do not create a revision plan, apply repairs, merge to main, or close the campaign by implication.
